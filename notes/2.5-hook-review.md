# 2.5 hook review

Phase 1, 2026-10-25. For each of the 19 `@wrapMethod` hooks in `docs/HOOKS.md`: the vanilla method as the mod last ran on it (game patch 2.12, mod 2.2.5) and as the 2.5 game and the build just before it ship it, plus what the change means for our wrap.

## Sources
- **2.12**: `game-folder-backup/2026-10-25_pre-2.5-cleanup/r6/cache/final.redscripts.modded` (2024-04-27), the bundle the game compiled with 2.2.5 installed, decompiled with `redscript-cli 0.5.32 decompile -f`. In a modded bundle a wrapped method `M` becomes a stub that calls `wrapper$N` (our code), and the vanilla body survives as `proxy$N+1`; the review compares that proxy body. Two decompiler artifacts show up in every proxy and are **not** game changes: the `cb` flag is missing (`protected func OnInitialize` vs `protected cb func OnInitialize`) and `super.X(...)` reads as `this.X(...)`.
- **pre-2.5** and **2.5**: the `game-scripts` repo tags (vanilla bundles).
- Comparison scripts were one-off (body text per method); not kept in the repo.

The game also calls the wrapped methods from the same number of places on pre-2.5 and 2.5 (e.g. `SwitchTriggerMode` 1, `IsPrimaryTriggerModeActive` 4, `GetDesiredAttackRecord` 4, `SpawnAttackGameEffect` 2).

**Conclusion:** 2.5 (and the patches between 2.12 and 2.5) left the wrapped methods' logic alone. The one change that touched our behaviour (touch `tap`) is fixed. Risk now sits around the hooks rather than in them:
- **Dual-wielding (new in 2.5).** `WeaponObject` gained `IsEquippedInLeftHand`, `GetStateMachineBlackboardID`, `GetAttachedSlotID`; `gameItemData.CanDualWield` checks the `DualWield` tag and the Cool milestone perk; `weaponTransitions.script` changed +432/−159 lines elsewhere in the file. Our weapon wraps read "the" weapon through `GetWeaponObject(scriptInterface)`. Covered by the dual-wield task.
- Behaviour inside the TweakDB (stat records, attack packages) isn't visible in scripts; the self-check covers record wiring, the crafting end-to-end task covers results.

## Related finding (not a hook change)
`CraftItem` (our wrap) swaps the crafted record to `<weapon>_Preem<Evolution>` when an evolution barrel is chosen, without checking that the variant exists. `PreemWeaponAlteration` makes variants only for ranged weapons whose own evolution is Smart, Tech or Power, so a ranged weapon with any other evolution (or none) would hand a null record to vanilla `CraftItem`. A guard task was added below the hook review task.

## Dual-wielding (2.5), static check
Added 2026-10-25 for the dual-wield task. Not played yet (no save on this PC); in-play behaviour is on the Phase 1 gate.

How 2.5 runs two weapons: each equipped weapon has its own weapon state machine. A transition reaches its weapon through `WeaponTransition.GetWeaponObject(scriptInterface)`, which is `scriptInterface.owner as WeaponObject`, the weapon that owns that state machine instance. The left hand has its own slot (`AttachmentSlots.WeaponLeft`) and blackboard entry (`PlayerStateMachine.LeftWeapon`, chosen by the new `WeaponObject.GetStateMachineBlackboardID`). Which weapons can be dual-wielded: `gameItemData.CanDualWield` = tag `DualWield` + the Cool milestone perk, unless the quest blocks it.

What that means for our hooks:
- `WeaponObject.OnGameAttached` runs per weapon object; the left weapon's owner is the player too, so `ChangeTriggerBasedOnPreemMods` sets each weapon's trigger mode from its own mods.
- `WeaponTransition.SwitchTriggerMode`, `IsPrimaryTriggerModeActive`, `GetDesiredAttackRecord` all take the weapon from `GetWeaponObject(scriptInterface)`, so each hand uses its own mods. `GetDesiredAttackRecord` caches the attack package in `this.m_rangedAttackPackage`, which vanilla does too, so it is per state machine as in vanilla.
- Melee wraps use `MeleeTransition.GetWeaponObject(scriptInterface)` the same way.
- Nothing in the mod's runtime code looks up "the active weapon" (`GameObject.GetActiveWeapon`, `GetItemInSlot(WeaponRight)`); only the dev dump command does.

Conclusion: no code change needed; by construction each hand's weapon gets its own trigger mode and attack. To confirm in play (gate): two Preem-modded handguns with different trigger mods (e.g. one Full-auto, one Burst) fire in their own modes; a Smart-barrel handgun in one hand and a plain one in the other.
