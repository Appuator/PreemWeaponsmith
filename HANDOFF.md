## 1. Architecture map
All paths are under `src/redscript/PreemWeaponsmith/`. Modules are `PreemCrafting.*`.

| Area | Classes / modules | Notes |
|---|---|---|
| Core data | `PreemMod`, `PreemSlot`, `PreemStats` (`Core/BaseItems.reds`); `PreemModStyleType`, `PreemModClassType` etc. (`Core/BaseEnums.reds`) | Style enum values are grouped by hundreds per slot class (Barrel 0–19, Trigger 100+, Mag 200+, Sight 300+, Blade 400+, Handle 500+). Code relies on those ranges. |
| Settings | `PreemSettings` (`Core/PreemSettings.reds`, `ScriptableSystem`), `PreemModSettings` (`Core/PreemModSettings.reds`) | `PreemSettings` holds the per-save values in `persistent` fields (unlock mode, limit mode, slot layout); a save without values starts from `new PreemModSettings()`, whose `@runtimeProperty("ModSettings.*")` fields Mod Settings fills when installed (built-ins otherwise: unlock = WeaponBlueprints, limit = Sandbox, layout = on weapon). Only `PreemSettings` reads `PreemModSettings`; `PreemModUnlocker` gets the modes injected (`SetModes`). |
| Settings panel | `PreemSettingsPopup` (`PreemMainUI/PreemUI/PreemSettingsPopup.reds`); `PreemSlotFrame.CreatePreemSettingsButton`, `OnPreemSettingsClicked`, `ApplyPreemSettings` (`PreemMainUI/PreemSlotFrame.reds`) | A SETTINGS button (top right of the Preem slot frame's container) opens a `BasePreemMenuPopup` with one button per setting; each press cycles that `PreemSettings` value and calls `ApplyPreemSettings`, which clears the chosen mods, rebuilds both slot frames (the layout picks the grid shape), keeps the frame that was showing, recreates the button on top and asks the host to refresh (the craft button). Esc closes the popup. |
| Mod catalogue | `PreemModMaker` (`CraftingSystem/PreemModMaker.reds`) | Static factory: style type → `PreemMod` with requirements, incompatibilities and description text. All mod text lives here. |
| Mod ↔ game item mapping | `PreemModMapper` | Maps a `PreemMod` to its TweakDB item (`Items.Preem…`) and attachment slot(s) (`AttachmentSlots.Preem…01/02`). |
| Slot rules | `PreemModSlotManager`, `PreemCraftingSystem.AreModsCompatible` | `CanInstallPreemModInSlot` checks slot class and required mods among the slotted mods. Incompatible styles and required evolution are checked for the whole chosen set by the pure static `PreemCraftingSystem.AreModsCompatible(mods, weaponEvolution)` (called from `CanInstallSelectedPreemMods`). Also tracks the selected and hovered slot for the UI. |
| Progression | `PreemModUnlocker` | Sandbox vs Blueprints. Static per-rarity unlock lists (Common … Legendary++) and the mod-amount limit. |
| Crafting system | `PreemCraftingSystem` (`ScriptableSystem`) | Holds the mods chosen for the current craft. `ApplyMods` puts them on a `gameItemData`, new (crafting) or owned (upgrade screen): `PlanModSlots` (pure: slot per mod, 2.2.5 order, Silencer in `PowerModule`) and `PlanModChanges` (pure: keep mods already in place, install the rest, empty slots whose mod is no longer chosen) against `GetInstalledMods(itemData)` (read-back of the Preem slots and the muzzle slot as `PreemModPlacement`s); removals go through `CraftingSystem.RemovePreemMod`, which deletes the mod item (no refund). Reached via `GetInstance(gameInstance)`. `GetCraftRecord(itemRecord, modTypes)` (pure static) picks the record `CraftItem` crafts: `<id>_Preem<Evolution>` for an evolution barrel, the weapon itself when that variant doesn't exist. |
| Game hooks: crafting | `PreemCraftingSystemAdapter` | Wraps `CraftingSystem.CraftItem` (swaps to the evolution variant record and installs mods), `CanItemBeCrafted`, `EnoughIngredientsForCrafting`. Adds `InstallPreemMod`. |
| Game hooks: inventory | `PreemInventoryAdapter` | Wraps `InventoryDataManagerV2` / `UIInventoryItemModsStaticData` slot queries so Preem slots show or hide correctly in the inventory UI. |
| Game hooks: weapon | `PreemWeaponAdapter`, `ItemDataAdapter` | `WeaponObject.OnGameAttached` sets the trigger mode from installed mods; `WeaponTransition` wraps choose the attack record and trigger mode; melee wraps add blade/handle effects. `gameItemData.DoesItemHave*` helpers. |
| Crafting UI | `PreemSlotFrame.reds` (`PreemSlotFrame`: slots, ranged/melee grids, mod selector popup, SETTINGS button; `PreemSlotFrameHost`: what a screen supplies), `PreemWeaponPreviewContainer.reds` (crafting host: one `_preemFrame` field on `CraftingMainGameController`, `PreemCraftingScreenHost`, the recipe-selection and craft wraps), `PreemUI/*`, `PreemUIBase/*` | The frame is a plain class any screen can host in a container widget; the host gives it the popup requester, player, tooltips manager and weapon rarity, and gets `OnPreemModsChanged`/`ClearPreemMods` calls back. Slots and grids are built in code with Codeware `inkCustomController`. The `PreemModSelectorPopup` (Codeware `CustomPopup`) lists mods. `MaterialTooltip.SetData` wrap adds mod descriptions. |
| Upgrade screen | `PreemMainUI/PreemUpgradeScreen.reds` (wraps on `UpgradingScreenController`: `Init`, `UpdateItemPreviewPanel`, `GetUpgradableList`; `PreemUpgradeScreenHost`) | The Upgrades tab hosts a `PreemSlotFrame` as a one-row strip (`UseStripLayout`, no SETTINGS button) between the comparison tooltips and the UPGRADE button, inside a filling canvas because the details container stretches its children. Selecting a weapon shows its installed mods (`ShowInstalledMods` from `GetInstalledMods`). The list adds every owned weapon of a Preem type that is non-iconic or max tier (vanilla lists only iconics below max tier), and the preview is re-shown for those. Evolution barrels show disabled (`IsModAllowedOnOwnedWeapon`). The hold button (`RefreshPreemButton`, `OnHoldFinished` wrap): an iconic below max tier reads UPGRADE and needs vanilla's checks plus allowed mods (`PreemCraftingSystem.CanInstallMods`: compatibility and the limit for the rarity after the upgrade); its mods are stored with `SetUpgradeMods` and applied by the `CraftingSystem.UpgradeItem` wrap (same `ItemID`, vanilla raises `WasItemUpgraded`). The added items read APPLY, hide ingredients, and only `ApplyModList` runs (vanilla's hold is skipped: it would charge and raise their tier). Installs are queued, so the strip shows `GetShownMods` (the last applied set) until the menu reopens (`ForgetLastApplied`). Unlock rarity: the next quality for an upgradable iconic, else the current one. Dev drivers: `PreemUiNextTab`, `PreemUiSelectUpgrade`, `PreemUiSelectUpgradeTestItem`, `PreemUiDumpUpgrade` (an item scrolled out of the virtual list needs the driver to preview it from its data). |
| TweakDB | `tweaks/*.yaml` (repo root; TweakXL, installed as `r6/tweaks/PreemWeaponsmith/`), `PreemWeaponAlteration` (`ScriptableTweak`, `Tweaking/`) | YAML (every fixed record): the 10 Preem attachment slots (`slots.yaml`), 11 blueprint elements (`blueprint-elements.yaml`), every mod and its stat records (`barrels.yaml`, `triggers.yaml`, `magazines.yaml`, `melee.yaml`), and `Items.TestMod1`, the item `PreemModMapper` falls back to for an unmapped style (`fallback.yaml`). The Smart, Tech and Power barrels take vanilla stat lists with `!append-from`; TweakXL applies plain `!append` before every `!append-from`, hence the helper list `PreemWeaponsmith.SmartBarrelOwnStats`. TweakXL loads the YAML before any `ScriptableTweak` runs. Alteration: loops over every weapon, adds Preem slots and creates `_Preem<Evo>` evolution variants (`CloneVariant`: registered names when the base has one), then `SetEvolutionMarkers` gives each variant its new evolution's tags, secondary trigger (Charge on Tech; Smart and Power keep the base's), preview effect and `Price.<Evolution>Weapon` entry, as vanilla weapons of that evolution have them, and `AddEvolutionStatModifiers` appends to `statModifiers` what the pure `EvolutionStatModifiers` (RedTest) returns: the undo records for the old evolution's DPS and Smart headshot penalties (`PreemWeaponsmith.Undo*` in `evolution-stats.yaml`) and vanilla's own penalty records for the new one, picked by the class group `Items.Base_<Evolution>_<Class>_Mult_Stats` the variant keeps. `statModifierGroups` stay the original's (decisions log 2026-10-27: only DPS and headshot change). The same loop covers EnhancedCraft's `Items.Craftable_*` variant records when it is installed; there is no EnhancedCraft-specific code since the Phase 1 gate. Proof that a move changed nothing: the record dump (dev tooling below). |
| Sound archive (retired) | `archive/PreemWeaponsmith.archive`, built from `wolvenkit/` | Not shipped since Phase 3 (fire-mode sounds above replace it). It replaced the whole `base\sound\metadata\cooked_metadata.audio_metadata`. Kept only as input to `dev/spike/audioware/event-map.py`. Event list: `docs/weapon-sound-events.txt`. |
| Fire-mode sounds | `PreemSoundSets` (`Fills`, `Patch`) and `PreemSoundSetService` (`Audio/PreemSoundSets.reds`, module `PreemCrafting.Audio`) | A `ScriptableService` that registers for Codeware's `Resource/Ready` on the `base` and `ep1` `cooked_metadata.audio_metadata`. It sets only the empty fire-mode fields of the named player sound sets to other weapons' existing events, and logs `[PreemWeaponsmith] sound sets: N fields set in <path>`. Table source: `notes/audioware-sounds.md` "Event map" (ADR 0001). The table holds 222 fills: the event map's 191 (137 on plain sets: auto loop + stop on 23, burst on 44, charge start on 43, Grit charge ready, Defender perk trio; 54 on the 18 `_suppressor` sets) and 31 gap fills on 16 sets that 2.2.5 also left empty (Phase 3 gate; donors in `notes/audioware-sounds.md` "Gap fills", rows in `dev/spike/audioware/gap-fills.tsv`). 199 fields in base, 23 in ep1. A weapon with a silencer (the Preem `Barrel_Silencer` on the Liberty, Kyubi and Ajax, or a built-in one) plays from its `_suppressor` set. |

## 4. Bugs & fixes (chronological)

## 5. Verification notes
- redscript compiles all mods at game start; errors go to `r6/logs/redscript_rCURRENT.log`. On 2.5, if compilation fails the game shows an error popup, never reaches the main menu, and the engine watchdog crashes it after 120 s (`Watchdog timeout! (120 seconds)` in the RED4ext log). Tested 2026-10-25 with a broken scratch script.
- Logging from scripts (tested 2026-10-25 on 2.5): `Print(...)` (Codeware) lands in CET's `bin\x64\plugins\cyber_engine_tweaks\scripting.log`. `FTLog`, Codeware `ModLog` and `Print` all land in CET's `gamelog.log` (the Game Log window); `Print` also lands in `scripting.log` (the console). Correction (2026-10-25): an earlier note here said `FTLog`/`ModLog` wrote nowhere, because `gamelog.log` was checked while the game was still running. CET writes its logs (`gamelog.log`, `scripting.log`, a mod's own `spdlog` log) **only when the game exits**, so they can't be polled during a run. For live signals, a CET mod writes a file in its own folder with `io.open` (that is how the boot check's marker works).
- Main menu timing on 2.5: `SingleplayerMenuGameController.OnInitialize` runs about 25 s after launch, while the intro video still plays over it. The menu is visible at about 150 s. `-skipStartScreen` does not skip the intro or the "press any key" prompt. Closing the window (`CloseMainWindow`) at that point exits cleanly in about 7 s and flushes every log. First launch after 2.5 also showed CDPR's new user agreement and CET's overlay-key setup; the user handled both (the CET overlay key is Ctrl+Q).
- `ScriptableSystem`s attach at the main menu, with no save loaded: `PreemDevSystem.OnAttach` logs about 26 s after launch, 1 s before the main menu controller initializes (2026-10-25). They attach **again** when a save loads (a new session; `PreemDevSystem attached` is logged twice in a `-LoadSave` run), so per-session state starts fresh. RedTest is set up in `OnAttach` and runs its tests on Codeware's pre-game `Session/Ready` event, so tests run at the main menu. Results go to `gamelog.log` (`PASS:`/`FAIL:` lines, then `Tests: X failed, Y passed, Z total`, printed twice); the boot check parses them (`tools/RedTestLog.psm1`).
- Debugger: redscript-dap 0.0.8 (latest, 2025-08) crashes 2.5 on load, so there are no breakpoints for now. Re-test when it publishes a 2.5 build: put the DLL in `red4ext\plugins\`, put a scratch `@wrapMethod(SettingsMainGameController) OnInitialize` hook in `r6\scripts\` (it fires when Settings opens from the main menu, no save needed, and compiled cleanly on 2.5), run VS Code `Redscript: Attach to Cyberpunk 2077`, set the breakpoint on a line with a function call, then open Settings. Until then: `Print` logging (lands in CET `scripting.log`, read after the game exits). Hot reload is also unavailable, because `red-cli watch` needs RedHotTools, which is disabled for the same reason.
- At the main menu (no save loaded) `GetPlayer(gi)` already returns a player object, and `TransactionSystem.GiveItem`/`GetItemData` work on it. But `ItemModificationSystem` install requests and `EquipmentSystem` equip requests are never processed there (checked 2026-10-25 with `dev/cet/debug-smoke.lua`: 0 mods installed after 8 s, weapon never active). Anything that installs or equips needs a loaded save **past its loading screen**: after a load the game waits on "Press Space to continue" with the world paused, and queued requests stay unprocessed until then (seen in a screenshot, 2026-10-25). The user's test save is `ManualSave-74` (made 2026-10-25, near the start of a new game); `ManualSave-75` was made from it by the settings save/load check (Preem settings `0, 1, 1`) and is now the newest, so `-LoadSave` loads that one.
- CET's `gamelog.log` is capped: a run that logged about 11400 self-check lines left a 6656-line file with lines missing (2026-10-25). Keep FTLog output per run small; the self-check prints PASS counts per kind and every FAIL. Counts in summary lines are computed in script, so they're reliable even when lines are dropped.
- In-game automation: `pwsh tools/boot-check.ps1 -Run <file.lua> -HoldSec <s>` installs a Lua file as a one-off CET mod (`PreemBootRun`) and keeps the game open after the main menu; `[PreemDev]` lines (FTLog) are printed from `gamelog.log` after exit. Add `-LoadSave` to load the newest save first: the marker mod loads it from the main menu, the boot check presses Space on the loading screen (the game window takes keyboard focus), and the run continues once game time moves (about 2 min after launch). A `-Run` script should wait for moving game time itself (`dev/cet/debug-smoke.lua`).
- Loading a save other than the newest from the main menu (2026-10-25, Phase 1 gate #7 `[!]`): `SingleplayerMenuGameController.OnSavesForLoadReady(saves)` lists the save folder names newest first (autosaves included; `AutoSave-3` was first, `ManualSave-75` third), and that position is the index `LoadModdedSave` takes. The main menu gets `OnSaveMetadataReady` only for index 0. `LoadModdedSave(n)` for n > 0 opens the game's native "Mod verification" confirmation, even for a save made with the current mods, and that popup is not a `GenericMessageNotification` (observing its `OnInitialize` caught nothing). Continue (index 0) doesn't ask.
- Booting without an optional dependency: `pwsh tools/boot-check.ps1 -Without 'Mod Settings'` moves that pin's plugin folder to `game-folder-backup/boot-without/` for the run, skips it in the dependency check, and always moves it back (also at the start of the next run if a run was interrupted). Tests that only make sense without Mod Settings use `@if(!ModuleExists("ModSettingsModule"))`.
- `r6\scripts` sometimes briefly shows empty `Codeware` and `TweakXL` folders (seen once at the start of a boot check, 2026-10-25, after the previous boot; gone after the next one; redscript compiled nothing from them). They aren't ours and don't affect the mod. Probably the frameworks create and remove empty legacy folders themselves. Ignore them in the boot check's "script mods" list.
- Driving the UI (2026-10-25): injected mouse input (`SetCursorPos`, relative and absolute `mouse_event`) doesn't move the game's own software cursor reliably, so clicks can't be scripted from outside.
