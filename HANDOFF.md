## 1. Architecture map
All paths are under `src/redscript/PreemWeaponsmith/`. Modules are `PreemCrafting.*`.

| Area | Classes / modules | Notes |
|---|---|---|
| Core data | `PreemMod`, `PreemSlot`, `PreemStats` (`Core/BaseItems.reds`); `PreemModStyleType`, `PreemModClassType` etc. (`Core/BaseEnums.reds`) | Style enum values are grouped by hundreds per slot class (Barrel 0–19, Trigger 100+, Mag 200+, Sight 300+, Blade 400+, Handle 500+). Code relies on those ranges. |
| Settings | `PreemSettings` (`Core/PreemSettings.reds`, `ScriptableSystem`), `PreemModSettings` (`Core/PreemModSettings.reds`) | `PreemSettings` holds the per-save values in `persistent` fields (unlock mode, limit mode, slot layout); a save without values starts from `new PreemModSettings()`, whose `@runtimeProperty("ModSettings.*")` fields Mod Settings fills when installed (built-ins otherwise: unlock = WeaponBlueprints, limit = Sandbox, layout = on weapon). Only `PreemSettings` reads `PreemModSettings`; `PreemModUnlocker` gets the modes injected (`SetModes`). |
| Settings panel | `PreemSettingsPopup` (`PreemMainUI/PreemUI/PreemSettingsPopup.reds`); `CraftingMainGameController.CreatePreemSettingsButton`, `OnPreemSettingsClicked`, `ApplyPreemSettings` (`PreemMainUI/PreemWeaponPreviewContainer.reds`) | A SETTINGS button (top right of the Preem slot frame, `_preemContainer`) opens a `BasePreemMenuPopup` with one button per setting; each press cycles that `PreemSettings` value and calls `ApplyPreemSettings`, which clears the chosen mods, rebuilds both slot frames (the layout picks the grid shape), keeps the frame that was showing, recreates the button on top and refreshes the craft button. Esc closes the popup. |
| Mod catalogue | `PreemModMaker` (`CraftingSystem/PreemModMaker.reds`) | Static factory: style type → `PreemMod` with requirements, incompatibilities and description text. All mod text lives here. |
| Mod ↔ game item mapping | `PreemModMapper` | Maps a `PreemMod` to its TweakDB item (`Items.Preem…`) and attachment slot(s) (`AttachmentSlots.Preem…01/02`). |
| Slot rules | `PreemModSlotManager`, `PreemCraftingSystem.AreModsCompatible` | `CanInstallPreemModInSlot` checks slot class and required mods among the slotted mods. Incompatible styles and required evolution are checked for the whole chosen set by the pure static `PreemCraftingSystem.AreModsCompatible(mods, weaponEvolution)` (called from `CanInstallSelectedPreemMods`). Also tracks the selected and hovered slot for the UI. |
| Progression | `PreemModUnlocker` | Sandbox vs Blueprints. Static per-rarity unlock lists (Common … Legendary++) and the mod-amount limit. |
| Crafting system | `PreemCraftingSystem` (`ScriptableSystem`) | Holds the mods chosen for the current craft. `ApplyMods` installs them on the crafted `gameItemData`. Reached via `GetInstance(gameInstance)`. `GetCraftRecord(itemRecord, modTypes)` (pure static) picks the record `CraftItem` crafts: `<id>_Preem<Evolution>` for an evolution barrel, the weapon itself when that variant doesn't exist. |
| Game hooks: crafting | `PreemCraftingSystemAdapter` | Wraps `CraftingSystem.CraftItem` (swaps to the evolution variant record and installs mods), `CanItemBeCrafted`, `EnoughIngredientsForCrafting`. Adds `InstallPreemMod`. |
| Game hooks: inventory | `PreemInventoryAdapter` | Wraps `InventoryDataManagerV2` / `UIInventoryItemModsStaticData` slot queries so Preem slots show or hide correctly in the inventory UI. |
| Game hooks: weapon | `PreemWeaponAdapter`, `ItemDataAdapter` | `WeaponObject.OnGameAttached` sets the trigger mode from installed mods; `WeaponTransition` wraps choose the attack record and trigger mode; melee wraps add blade/handle effects. `gameItemData.DoesItemHave*` helpers. |
| Crafting UI | `PreemWeaponPreviewContainer.reds` (adds members to `CraftingMainGameController`), `PreemUI/*`, `PreemUIBase/*` | Builds the slot frame (ranged or melee) in code with Codeware `inkCustomController`. The `PreemModSelectorPopup` (Codeware `CustomPopup`) lists mods. `MaterialTooltip.SetData` wrap adds mod descriptions. |
| TweakDB | `tweaks/*.yaml` (repo root; TweakXL, installed as `r6/tweaks/PreemWeaponsmith/`), `PreemModCreation`, `PreemWeaponAlteration` (`ScriptableTweak`, `Tweaking/`) | YAML: the 10 Preem attachment slots (`slots.yaml`) and 11 blueprint elements (`blueprint-elements.yaml`), every mod and its stat records (`barrels.yaml`, `triggers.yaml`, `magazines.yaml`, `melee.yaml`); TweakXL loads it before any `ScriptableTweak` runs. ModCreation: about 370 clone/set calls creating fixed mod item and stat records (moves to YAML in Phase 2). Alteration: loops over every weapon, adds Preem slots and creates `_Preem<Evo>` evolution variants. The same loop covers EnhancedCraft's `Items.Craftable_*` variant records when it is installed; there is no EnhancedCraft-specific code since the Phase 1 gate. |
| Sound archive | `archive/PreemWeaponsmith.archive`, built from `wolvenkit/` | Full replacement of `base\sound\metadata\cooked_metadata.audio_metadata` adding auto-fire events. Event list: `docs/weapon-sound-events.txt`. |

## 4. Bugs & fixes (chronological)
*Format: YYYY-MM-DD: **Symptom** → root cause → fix (commit). End with the rule it teaches, if any; rules that apply every session are proposed for CLAUDE.md Gotchas (or an automated check) at phase end and added once approved at the gate.*

- 2026-10-25: **Game crashes about 2 s after launch, before the main menu (access violation 0xc0000005, Windows Application log event 1000)** → three RED4ext plugins with no 2.5 build crash the game while RED4ext loads them: Audioware 1.9.9, RedHotTools 1.3.0-rc.3 and redscript-dap 0.0.8. Each was isolated by the last `Loading plugin from ...` line in `red4ext\logs` before the crash. Mod Settings 0.2.22 was cleared as the cause: TweakXL loads fine right after it → fix: moved the three to `game-folder-backup\disabled\` (no commit; game folder only). Rule: a plugin released before a game patch is guilty until a boot shows it loading. Re-enable each one only after it publishes a build for the patch. (The boot check's dependency check should catch this automatically.)
- 2026-10-25: **Boot check crashes with "Method invocation failed because [System.Boolean] does not contain a method named 'Trim'" after a run where the game was killed early** → a killed run leaves one-line logs; PowerShell unrolls a one-element array returned from a function (`Get-RunLines`) or from `Get-Content` into a plain string, and `<string> -match` returns a Boolean instead of the matching lines → fix: wrap those results in `@(...)` in `tools/boot-check.ps1` (Phase 1 boot-check screenshot task). Rule: in PowerShell, wrap any function result or `Get-Content` that is filtered with `-match` in `@(...)`.
- 2026-10-25: **Self-check reported missing evolution variants for two unnamed weapon records (entity `smasher_launcher`), and the same records were sometimes treated as ranged and sometimes not** → `Jurij.Jurij_Launcher_Base` (an NPC launcher) has no item type record; `ItemType().Type()` through the null `wref` returns an undefined value, so in `PreemWeaponAlteration.OnApply` it read as a ranged type and got `_PreemTech`/`_PreemSmart` clones, while the self-check read it as `Clo_Face` → fix: both read the type only when `IsDefined(ItemType())`, else `Invalid` (Phase 1 self-check task). Rule: in redscript, never call a method through a record reference (`wref`) that may be null and use the result; check `IsDefined` first. Null calls don't throw, and the value they return can't be trusted.
- 2026-10-25: **`red-cli pack` (0.5.1) zip contains no mod code: 12 module files of about 80 bytes each plus one `PreemWeaponsmith.Global.reds`** → red-cli's bundler merges files by module. With this source tree it wrote only each module's header and kept only the files that have no `module` line (settings, tweaks); every hook and class in a module was lost. It also writes the zip to the repo root, not `dist/` → fix: `tools/pack-release.ps1` zips the source tree unchanged, like the 2.2.5 release, into `dist/` (Phase 1 release-candidate task). Rule: never ship a `red-cli pack` zip; check any release zip by installing it into the game and running the boot check.
- 2026-10-25: **(Latent, found in review; never seen in play) Crafting a weapon with an evolution barrel would hand vanilla `CraftItem` a null record when the weapon has no `_Preem<Evolution>` variant** → the `CraftItem` wrap swapped records without checking that the variant exists; only ranged weapons whose own evolution is Smart/Tech/Power get variants → fix: the rule moved to `PreemCraftingSystem.GetCraftRecord`, which falls back to the original record (RedTest `CraftRecord`, red first: `Katana + Smart barrel` failed before the fix).
- 2026-10-25: **(While building the settings panel) the SETTINGS button vanished after a setting changed** → `ApplyPreemSettings` removed the button's root widget from `_preemContainer` and called the Codeware controller's `Reparent` again, to put it above the rebuilt frames; the button was not shown afterwards (`PreemUiDump`: `settings button false`) → fix: create a new button instead (`CreatePreemSettingsButton`), like the frames. Rule: after `RemoveChild` on a Codeware `inkCustomController`'s root, recreate the controller rather than reparenting it.
- 2026-10-26: **The first record-dump baseline had no `statModifiers` or `placementSlots` lines at all, yet two boots matched and the slot move "passed"** → the dump takes flat names from a record class's parameterless getters; a list of record references has none (only `X(out list)`, `GetXCount()`, `GetXItem(i)`), so those flats were silently skipped. Found while planning the barrel move, by grepping the baseline for a flat the move changes → fix: `GetXCount` stands for flat `x`; baseline redone from the pre-Phase-2 scripts (2930 → 3838 flats) (Phase 2 element task). Rule: before trusting a comparison tool, check its output contains the very values the change touches; "identical" from a tool that can't see them proves nothing.
- 2026-10-26: **(Latent since before 2.5, found by the record dump) Turbo Charge and Omega Charge's charge-time stat (`Items.PreemBarrelMod{Turbo,Omega}Charge_inline3`) used `AdditiveMultiplier`, though the script set `modifierType` to `"Multiplier"`** → the script passed a String to `TweakDBManager.SetFlat` for a CName flat; a value of the wrong type is ignored without an error, so the base record's `AdditiveMultiplier` stayed. The YAML move applied `Multiplier` for real and the dump showed the change → not fixed: `tweaks/barrels.yaml` leaves the flat out (today's behaviour) until the gate decides (Phase 2 barrel task). Rule: a `SetFlat` value must have the flat's exact type (CName `n"..."`, not a String); the record dump is the way to see whether a set took effect.

## 5. Verification notes
- redscript compiles all mods at game start; errors go to `r6/logs/redscript_rCURRENT.log`. On 2.5, if compilation fails the game shows an error popup, never reaches the main menu, and the engine watchdog crashes it after 120 s (`Watchdog timeout! (120 seconds)` in the RED4ext log). Tested 2026-10-25 with a broken scratch script.
- Logging from scripts (tested 2026-10-25 on 2.5): `Print(...)` (Codeware) lands in CET's `bin\x64\plugins\cyber_engine_tweaks\scripting.log`. `FTLog`, Codeware `ModLog` and `Print` all land in CET's `gamelog.log` (the Game Log window); `Print` also lands in `scripting.log` (the console). Correction (2026-10-25): an earlier note here said `FTLog`/`ModLog` wrote nowhere, because `gamelog.log` was checked while the game was still running. CET writes its logs (`gamelog.log`, `scripting.log`, a mod's own `spdlog` log) **only when the game exits**, so they can't be polled during a run. For live signals, a CET mod writes a file in its own folder with `io.open` (that is how the boot check's marker works).
- Main menu timing on 2.5: `SingleplayerMenuGameController.OnInitialize` runs about 25 s after launch, while the intro video still plays over it. The menu is visible at about 150 s. `-skipStartScreen` does not skip the intro or the "press any key" prompt. Closing the window (`CloseMainWindow`) at that point exits cleanly in about 7 s and flushes every log. First launch after 2.5 also showed CDPR's new user agreement and CET's overlay-key setup; the user handled both (the CET overlay key is Ctrl+Q).
- `ScriptableSystem`s attach at the main menu, with no save loaded: `PreemDevSystem.OnAttach` logs about 26 s after launch, 1 s before the main menu controller initializes (2026-10-25). They attach **again** when a save loads (a new session; `PreemDevSystem attached` is logged twice in a `-LoadSave` run), so per-session state starts fresh. But `ItemModificationSystem` install requests and `EquipmentSystem` equip requests are never processed there (checked 2026-10-25 with `dev/cet/debug-smoke.lua`: 0 mods installed after 8 s, weapon never active). - In-game automation: `pwsh tools/boot-check.ps1 -Run <file.lua> -HoldSec <s>` installs a Lua file as a one-off CET mod (`PreemBootRun`) and keeps the game open after the main menu; `[PreemDev]` lines (FTLog) are printed from `gamelog.log` after exit. Add `-LoadSave` to load the newest save first: the marker mod loads it from the main menu, the boot check presses Space on the loading screen (the game window takes keyboard focus), and the run continues once game time moves (about 2 min after launch). A `-Run` script should wait for moving game time itself (`dev/cet/debug-smoke.lua`).
- Loading a save other than the newest from the main menu (2026-10-25, Phase 1 gate #7 `[!]`): `SingleplayerMenuGameController.OnSavesForLoadReady(saves)` lists the save folder names newest first (autosaves included; `AutoSave-3` was first, `ManualSave-75` third), and that position is the index `LoadModdedSave` takes. The main menu gets `OnSaveMetadataReady` only for index 0. `LoadModdedSave(n)` for n > 0 opens the game's native "Mod verification" confirmation, even for a save made with the current mods, and that popup is not a `GenericMessageNotification` (observing its `OnInitialize` caught nothing). Continue (index 0) doesn't ask.
- Booting without an optional dependency: `pwsh tools/boot-check.ps1 -Without 'Mod Settings'` moves that pin's plugin folder to `game-folder-backup/boot-without/` for the run, skips it in the dependency check, and always moves it back (also at the start of the next run if a run was interrupted). Tests that only make sense without Mod Settings use `@if(!ModuleExists("ModSettingsModule"))`.
- `r6\scripts` sometimes briefly shows empty `Codeware` and `TweakXL` folders (seen once at the start of a boot check, 2026-10-25, after the previous boot; gone after the next one; redscript compiled nothing from them). They aren't ours and don't affect the mod. Probably the frameworks create and remove empty legacy folders themselves. Ignore them in the boot check's "script mods" list.
- Driving the UI (2026-10-25): injected mouse input (`SetCursorPos`, relative and absolute `mouse_event`) doesn't move the game's own software cursor reliably, so clicks can't be scripted from outside. Drive the UI from script instead (the `PreemUi*` exec functions call the same handlers a click does) and check the result with a screenshot: `boot-check -Screenshot` saves `screen.png` in the run's log folder after the hold; for several moments, a `-Run` script writes marks to a file in its CET mod folder and an outside script screenshots on each mark. In the crafting list, select through vanilla `CraftingMainLogicController.Select(index)` (toggle, select, scroll, preview); `SelectItem` alone leaves the preview on the old item. Indices are over `m_dataView` (after the category filter); `m_dataView.GetItem(i)` is the item's `RecipeData`.
- Not automatable: judging how the UI looks and how weapons feel in combat. Those are human gates.
